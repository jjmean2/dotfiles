# 개념과 동작 원리

tmux-dev 가 왜 그렇게 동작하는지 설명한다. 사용 절차는 [작업별 안내](how-to.md), 설계 결정의 전체 기록은 플러그인의
`session-picker.md`, `worktree-picker.md` 를 본다.

## 세 층의 대응

tmux 는 세션 → 윈도우 → 패널의 세 층을 가진다. tmux-dev 는 이 층을 개발 작업의 세 층에 하나씩 대응시킨다.

```
tmux 세션 "dotfiles"   = 프로젝트   ~/dev/jwlee/dotfiles          ← prefix S
 ├─ 윈도우 "main"      = 워크트리   ~/dev/jwlee/dotfiles (메인)   ← prefix W
 ├─ 윈도우 "feat-a"    = 워크트리   ~/.local/share/tmux-dev/worktrees/dotfiles/feat-a
 │   └─ 패널           = 역할       셸 (레이아웃이 정한다)
 └─ 윈도우 "notes"     = 디렉토리   ~/notes
```

이 대응은 강제가 아니라 관례다. tmux-dev 는 tmux 를 대체하지 않는다.

- `prefix c` 로 만든 보통 윈도우도 그대로 쓴다.
- `tmux new -c <경로>` 로 만든 세션도 `prefix S` 가 경로로 찾아 준다.
- 저장소가 아닌 디렉토리의 세션도 정상이다.

## 세션은 이름이 아니라 경로로 찾는다

`prefix S` 에서 디렉토리를 고르면 그 경로의 세션을 다음 순서로 찾는다.

1. 세션 옵션 `@tmux-dev-path` 가 그 경로인 세션. tmux-dev 가 세션을 만들 때 붙인다.
2. 옵션이 없는 세션 중 시작 경로(`session_path`)가 그 경로인 세션. 순정 tmux 로 만든 세션이다.
3. 없으면 새로 만든다.

같은 경로의 세션이 여럿이면 가장 최근에 붙었던 세션으로 간다. 경로는 심볼릭 링크를 푼 실제 경로로 비교한다.

세션 이름은 표시용이다. 기본은 디렉토리 이름이고, 다른 경로의 세션이 같은 이름을 쓰고 있으면 부모 이름을 붙인다
(`app` → `work_app`). 그래서 세션 이름을 `prefix $` 로 바꿔도 tmux-dev 는 같은 세션을 찾는다.

## 워크트리 = 브랜치 = 윈도우

`prefix W` 의 `worktree` 모드는 브랜치 하나를 워크트리 하나와 윈도우 하나에 묶는다. 브랜치마다 체크아웃이 따로 있으므로
브랜치를 바꾸려고 작업을 stash 할 필요가 없고, 여러 브랜치에서 에이전트나 dev 서버를 동시에 돌릴 수 있다.

워크트리는 기본으로 저장소 밖 `~/.local/share/tmux-dev/worktrees/` 에 모인다. 워크트리는 저장소에서 파생된 체크아웃이고
오래 남는 것은 브랜치이므로, 도구가 관리하는 데이터 위치에 둔다. 이 위치는 눈에 잘 띄지 않으므로 정리는 피커의 `ctrl-x` 로 한다.

윈도우는 사용자 옵션 `@worktree` 로 워크트리 경로를 기억한다. 피커는 이 옵션으로 "이 워크트리의 윈도우가 이미 열려 있는가" 를
판정한다. 찾는 범위는 지금 세션 하나다.

`prefix S` 에서 워크트리 경로를 고르면 세션을 새로 만들지 않고, 메인 저장소 세션 안의 그 워크트리 윈도우로 간다.

## 피커는 결정만 한다

피커(fzf)와 그 콜백은 아무것도 만들지 않는다. "무엇을, 어떤 레이아웃으로, 만들지 여부" 를 정해 상태 파일에 적고 끝난다.
디렉토리·저장소·세션·윈도우 생성은 fzf 가 끝난 뒤 스크립트가 한다. 셸에서 `tmux-dev project <경로>` 를 부르는 것과 같은 경로를 탄다.

예외는 정리(`ctrl-x`)다. 정리는 피커를 연 채로 계속 쓰기 위해 피커 안에서 시작하고, tmux 서버의 백그라운드 작업으로 돈다.

## 찾기와 만들기를 나눈다

- `enter` 는 **열기만** 한다. 걸리는 항목이 없으면 아무것도 만들지 않고 안내를 띄운다.
- `alt-enter` 는 **친 이름으로 만든다.** 결과가 있어도 친 이름을 쓴다 (`dotfiles` 가 걸려도 `dot` 을 만들 수 있다).

처음에는 "걸리는 항목이 없으면 enter = 생성" 이었다. 그러면 찾을 때는 퍼지 조각을, 만들 때는 전체 경로를 쳐야 해서 두 입력
문법이 섞였다. 검색과 생성을 한 입력창에서 다루는 다른 앱(Obsidian 빠른 전환, VS Code 브랜치 전환 등)처럼 만들기를 별도 진입으로 분리했다.

만들기는 늘 한 번 확인한다. `prefix S` 는 위치 목록에서 위치를 고르는 `enter` 가 확인이고, `prefix W` 는 푸터에서 묻는다.

## 경로 입력은 접두 일치로 거른다

`/` 나 `~` 로 시작하는 검색어는 퍼지가 아니라 경로 접두 일치로 거른다. 퍼지 검색은 없는 경로를 쳤을 때 엉뚱한 디렉토리를
1등으로 올리기 때문이다. 예를 들어 홈 아래 디렉토리 7만여 개에서 없는 경로 `~/dev/test` 를 퍼지로 찾으면 3만여 개가 걸리고
`~/dev/opensources/yup/test` 가 1등이 된다. 접두 일치면 0개이므로 `enter` 가 "없는 경로" 를 안내하고 `alt-enter` 로 만들 수 있다.

상대 경로는 받지 않는다. 피커를 띄운 패널의 디렉토리에 따라 결과가 달라지기 때문이다.

## 탐색 범위

탐색은 홈 하나에서 깊이 제한 없이 한다. 대신 숨김 디렉토리를 뺀다(저장소 탐색은 `.git` 만 예외). 숨김 디렉토리 아래는 대부분
도구 캐시·데이터라 이것만 빼도 탐색 시간이 크게 준다 (이 머신 실측: 저장소 탐색 13.3초 → 1.4초). 목록은 fd 가 찾는 대로 흘려 넣으므로
첫 결과는 바로 뜬다.

## 머지 판정

`prefix W` 의 `merged` 는 "브랜치의 변경이 베이스 브랜치에 모두 들어 있다" 는 뜻이다. 머지 방식에 상관없이 판정한다.

| 머지 방식 | 판정 방법 |
|---|---|
| fast-forward, merge commit | 브랜치 끝이 베이스의 조상인가 (`for-each-ref --merged`) |
| rebase (커밋 해시가 바뀜) | 브랜치 고유 커밋의 patch-id 가 베이스 쪽에 모두 있는가 |
| squash | merge-base 와 브랜치 끝의 diff 전체를 한 커밋으로 본 patch-id 가 베이스 쪽에 있는가 |
| squash (위로 못 잡은 것) | 베이스에 브랜치를 머지해 보면(`git merge-tree`) 베이스 트리가 그대로인가 |

위에서부터 처음 맞은 방법이 행의 `merged` 뒤에 글자로 붙는다: 없음 = 조상, `·r` = rebase, `·s` = squash, `·t` = merge-tree.
마지막 방법은 squash 뒤 베이스가 근처 줄을 고쳐 diff 문맥이 달라진 경우, 스택 PR 이 차례로 squash 된 경우를 잡는다.
머지 시뮬레이션이 만드는 오브젝트는 임시 디렉토리에 쓰고 지우므로 저장소에 남지 않는다. 여전히 못 잡는 것: GitHub 에서만
생긴 커밋(리뷰 제안 반영 등)이 함께 squash 되고, 그 뒤 베이스가 같은 줄을 다시 고친 경우.

**기준 ref.** 로컬 베이스가 업스트림(`origin/main`)과 같거나 뒤처져 있으면 업스트림으로, 아니면 로컬로 판정한다. 업스트림이
둘 다를 담으므로 "로컬 main 또는 origin/main 에 들어 있으면 머지됨" 을 한 번의 계산으로 얻는다. 피커가 뜰 때 백그라운드에서
`git fetch --prune origin` 을 하고, 원격 ref 가 바뀌었으면 목록을 다시 읽는다. 그래서 GitHub 에서 PR 을 머지한 직후에도 pull 없이 `merged` 가 보인다.

판정은 행마다 git 을 여러 번 돌려 비싸다. 그래서 마커 없는 목록을 먼저 띄우고 마커는 뒤에서 얹으며, 결과는
`~/.cache/tmux-dev/` 에 커밋 해시 기준으로 캐시한다.

## 정리는 되돌릴 수 있게

`clean up` 은 브랜치를 지우기 전에 항상 `refs/archive/<날짜>/<브랜치>` 에 보관한다. 이 ref 는 `refs/heads` 밖이라 브랜치 목록에는
나오지 않지만 git 이 커밋을 지우지 않고 남긴다. 그래서 머지되지 않은 브랜치도 부담 없이 정리하고 필요하면 되살린다.

정리 순서는 윈도우 닫기 → 워크트리 제거 → 보관 → 브랜치 삭제다. 윈도우를 먼저 닫아 그 안의 셸, nvim, 에이전트를 먼저 끝낸다.

워크트리 제거는 빠르게 보이도록 두 단계로 한다. 먼저 같은 파일시스템의 `.trash/` 로 `git worktree move` 해서(이름 바꾸기라 즉시 끝난다)
목록과 원래 경로를 바로 비우고, 실제 삭제는 그 뒤에 한다. 중간에 끊겨 남은 것은 다음에 피커가 뜰 때 마저 지운다.

## 피커는 modal floating pane 이다

피커는 `display-popup` 이 아니라 `new-pane -O`(modal floating pane)로 뜬다. tmux 3.9 부터 팝업은 floating pane 을 여는 호환
명령으로만 남기 때문이다. 이 때문에 생기는 차이:

- 피커는 클라이언트가 아니라 윈도우에 속한다. 같은 윈도우를 보는 다른 클라이언트에도 보인다.
- 피커가 떠 있는 동안은 그 윈도우의 다른 패널을 만질 수 없다.
- 피커 안에서는 prefix 를 포함한 모든 키가 피커로 가므로 피커가 겹쳐 뜨지 않는다.
- `esc` 는 tmux 가 아니라 fzf 가 받는다. 그래서 겹쳐 뜬 목록에서 `esc` 가 "한 단계 뒤로" 로 동작한다.

키를 누른 클라이언트를 정확히 전환하기 위해 `prefix S`·`prefix W` 는 피커를 직접 띄우지 않고 런처(`tmux-dev open`)를 거친다.
런처가 클라이언트 이름, 화면 가운데 자리, 크기, 스타일을 계산해 넘긴다.

## 레이아웃의 기본값이 셸 하나인 이유

레이아웃은 새 윈도우를 만들 때 한 번만 적용된다. 전역 기본값은 가장 단순한 `plain`(셸 하나)이다. 어떤 배치가 필요한지는
저장소마다 다르므로, 필요한 곳에만 저장소 기본값(`git config tmux-dev.layout`)이나 `alt-l` 로 더한다.
nvim 이나 dev 서버를 늘 띄우고 싶다면 전역 `@tmux-dev-layout` 을 바꾼다.

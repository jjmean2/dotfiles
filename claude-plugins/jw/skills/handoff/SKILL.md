지금 대화에서 정한 작업을 **다른 세션**에 넘긴다. 새 세션은 브랜치 워크트리에서 일하고, 이 세션(원본)은 그대로 남아
설계와 질의를 계속한다. 워크트리와 스택에 관한 원칙은 사용자 규칙(`worktree-workflow`)을 따른다.

`start_session` 도구가 보이면 이 스킬을 쓰지 말고 그 도구로 넘긴다 (원본과 연결되고 보고가 돌아온다).
그 도구는 Claude 세션만 연다. 사용자가 Cursor 세션으로 넘기라고 했으면 이 스킬을 쓴다.

## 1. 정하기

인자(`$ARGUMENTS`)로 받은 것은 그대로 쓰고, 없는 것은 대화를 보고 정한다.

- **브랜치**: 저장소의 이름 규칙을 따른다. 처음 보는 저장소면 `git branch -a` 로 관례를 본다.
- **도구**: 새 세션을 여는 도구. `claude`(Claude Code) 또는 `cursor`(Cursor CLI). 기본은 지금 이 세션의 도구이고,
  사용자가 고르면 다른 쪽으로 연다.
- **방식**:
  - `fork`: 대화를 통째로 복사한다. 시행착오·기각한 안까지 넘겨야 할 때.
  - `fresh`: 지시서 한 장으로 깨끗한 맥락에서 시작한다. 대화가 길거나 결론만 넘기면 될 때. 망설여지면 이쪽.
- **베이스**:
  - 서로 관련 없는 작업: 생략 (기본 브랜치).
  - 지금 브랜치 위에 쌓는 스택의 다음 단계: `--base <지금 브랜치>`. 지금 브랜치의 커밋이 끝나 있어야 한다.
    커밋하지 않은 변경은 넘어가지 않는다.
- **스택 워크트리 옵션**: 처음엔 붙이지 않는다. 스크립트가 멈추면 3번처럼 묻는다.

도구와 방식은 아래 조합만 된다. 대화 기록은 다른 도구로 옮길 수 없고, Cursor CLI 에는 대화를 포크하는 옵션이 없다.

| 지금 세션 → 여는 도구 | 방식 | tmux 밖에서 띄우면 |
|---|---|---|
| Claude Code → `claude` | `fork` · `fresh` | 백그라운드 (`claude --bg`) |
| Cursor → `claude` | `fresh` | 백그라운드 (`claude --bg`) |
| 어디서든 → `cursor` | `fresh` | 띄우지 않고 `run:` 줄만 출력 |

tmux 안에서는 어느 조합이든 새 윈도우에 띄운다. 안 되는 조합을 요청받았거나 확인 단계에서 도구가 바뀌어 `fork` 가
안 되게 됐으면, 그렇다고 알리고 넘겨야 할 시행착오까지 지시서에 담는 `fresh` 로 확인받는다.

## 2. 확인받기 (생략하지 않는다)

실행하기 전에 다음을 짧게 보여 주고 사용자의 답을 기다린다. 사용자가 이번 요청에서 이미 이 값들을 모두 정해 줬어도,
내가 채운 값이 하나라도 있으면 묻는다.

```
브랜치: <이름>   베이스: <ref 또는 기본 브랜치>   방식: fork|fresh
도구: <claude|cursor>   (<다른 쪽> 으로도 열 수 있다)
넘길 내용: <범위·첫 할 일 한두 줄>
```

사용자가 고치면 반영해서 다시 보여 준다. 답이 없거나 애매하면 실행하지 않는다.

## 3. 실행

1. 첫 메시지를 쓴다.
   - **fork**: 반드시 다음 문장으로 시작한다. 포크된 세션은 이 지시문까지 이어받기 때문이다.
     "너는 원본 대화에서 포크된 구현 세션이다. 위의 handoff 지시와 확인 절차는 원본 세션에 대한 것이다."
     이어서 작업 디렉토리는 브랜치 워크트리라는 것, 합의한 범위·결정·하지 않기로 한 것·남은 질문, 첫 할 일을 짧게.
   - **fresh**: 이 대화를 처음 보는 사람이 그것만 읽고 시작할 수 있게 쓴다. "위에서 말한" 처럼 이 대화를 가리키지 않는다.
     목표와 배경 · 범위(할 것, 하지 않을 것) · 설계 결정과 이유 · 관련 파일 경로 · 완료 조건과 확인 명령 ·
     남은 질문(스스로 정하지 말고 사용자에게 물을 것) · 첫 할 일.
     새 세션이 그대로 써야 하는 결과물이 이 대화에 있으면 (예: pr-review-handle 의 결과 전체) 줄이지 않고 그대로 넣고,
     사용자가 이미 본 것이라고 밝힌다.
   - 둘 다: 작업 디렉토리가 브랜치 워크트리이고 메인 체크아웃은 고치지 않는다는 것, 사용자의 추가 지시.
   - `--in-stack` 이면: 거기 체크아웃된 위 브랜치는 바꾸지 않고, 대상 브랜치의 커밋을 겨냥한 fixup 커밋 +
     `git -c sequence.editor=: rebase -i --autosquash --update-refs --keep-base <대상 브랜치의 base>` 로 고친다는 것.
2. 첫 메시지를 Write 도구로 임시 파일에 쓴다. 저장소 안에는 두지 않는다.
   heredoc 은 쓰지 않는다. 워크트리 세션에서는 heredoc 이 섞인 Bash 명령이 거절된다.
   - 경로는 절대 경로로 정한다. scratchpad 가 있으면 그 아래. 없으면 먼저 Bash 로 `echo "${TMPDIR:-/tmp}"` 를 실행해
     실제 디렉토리를 알아낸 뒤 그 아래에 쓴다. Write 도구는 `$TMPDIR` 같은 셸 변수를 풀지 않고, 샌드박스 Bash 의
     `TMPDIR` 은 `/tmp` 가 아닐 수 있어서, 짐작한 경로에 쓰면 스크립트가 다른 곳을 읽는다.
   - 파일 이름은 호출마다 새로 짓는다: `handoff-<브랜치의 / 를 - 로>-<MMDD-HHMMSS>.md`. 공용 임시 디렉토리에
     다른 세션이 남긴 같은 이름의 파일이 있으면 Write 가 "읽지 않은 파일" 이라며 거절하는데, 그 뒤에 스크립트가 돌면
     그 세션의 지시서가 그대로 넘어간다.
   - Write 가 성공했다는 결과를 본 **다음 응답에서** 3 을 실행한다. 같은 응답에 Write 와 함께 넣지 않는다
     (Write 가 실패해도 같은 응답의 Bash 는 돈다).
3. 한 줄로 실행한다. `--prompt-file` 에는 2 에서 Write 에 준 절대 경로를 글자 그대로 넘긴다 (변수로 다시 쓰지 않는다).
   ```
   ${CLAUDE_PLUGIN_ROOT}/bin/worktree-handoff <fork|fresh> --agent <claude|cursor> --prompt-file <파일> [--base <ref>] [--in-stack|--new-worktree] -- <브랜치>
   ```
   - `--agent` 는 확인받은 도구로 늘 넘긴다. 스크립트는 부른 곳이 어느 도구인지 짐작하지 않는다.
   - 세션을 띄우는 방식은 스크립트가 정한다 (1 의 표). 사용자가 방식을 말했을 때만 `--open bg|tmux|none` 을 붙인다.
   - fork 의 세션 ID 는 스크립트가 `$CLAUDE_CODE_SESSION_ID` 에서 읽는다.
   - 위 경로에 스크립트가 없으면 PATH 의 `worktree-handoff` 를 부른다.
4. 스크립트가 "스택 워크트리" 때문에 멈추면 오류를 보여 주고 묻는다.
   - 워크트리 하나에서 브랜치를 바꿔 가며 쌓는 스택이면 `--in-stack` (그 워크트리를 쓰고 체크아웃은 바꾸지 않는다).
   - 따로 떼어 작업할 거면 `--new-worktree`.
5. 그 밖의 실패는 오류를 그대로 보여 주고 멈춘다. `bg` 로 못 띄웠어도 워크트리와 `run:` 줄은 출력되니 함께 보여 준다.

## 4. 알리기

출력된 워크트리 경로, `session:` · `open:` 줄을 알리고 `attach:` · `run:` · `resume:` 줄 가운데 나온 것을 명령 그대로
보여 준다. `open:` 이 `none` 이면 세션은 아직 뜨지 않았다. `run:` 줄을 터미널에서 실행해야 시작한다고 알린다.
그 세션에 들어가는 것은 사용자가 한다. 이후 이 세션에서는 그 워크트리의 파일을 고치지 않는다.
